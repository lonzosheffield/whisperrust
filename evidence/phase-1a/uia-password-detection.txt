I-8 UIA password detection - live verification
==============================================
Date: 2026-09-20

BEFORE: target.rs checked only GWL_STYLE & ES_PASSWORD. Browser and Electron
password fields are not Win32 controls and carry no style bits, so they were
reported as is_password=false and dictation WOULD HAVE BEEN TYPED into them.
REDTEAM B-02 was unmitigated in exactly the applications where people most
often type passwords.

AFTER - measured:

  Control case (Windows Terminal, ordinary text target):
    exe        : windowsterminal.exe
    password   : no
    method     : Unicode

  Browser password field (local autofocused <input type="password">):
    exe        : msedge.exe
    title      : WhisperRust B-02 check ... - Microsoft Edge
    focus hwnd : Some(1903180)
    password   : yes      <-- previously reported "no"

  preflight() maps Yes -> Decision::Drop. The text is discarded entirely and
  is NOT placed on the clipboard, because relocating a credential to the
  clipboard is not a mitigation.

LATENCY: 5 full --probe invocations (each including process start, model-free)
took 626 ms total, so the UIA round trip is well inside the 120 ms budget.

NON-BLOCKING: the UIA COM apartment lives on its own thread and answers over a
channel with a hard timeout. The caller - which runs on the hook-owning thread -
can never block longer than UIA_TIMEOUT. Calling UIA inline would have
reintroduced defect D-4 (a sleeping hook thread freezes the whole keyboard).

TRI-STATE: a timeout yields Unknown, not No. Unknown degrades to clipboard-only
rather than typing, per I-9 "when unsure, do not inject". Collapsing Unknown
into No would have silently reintroduced B-02 on precisely the slow, busy
applications most likely to time out.
